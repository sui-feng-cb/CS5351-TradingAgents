## 2. A：FR-A 同日双标的对照报告

**目标**：让用户在同一分析日期并列查看两个标的的现有分析结果，方便比较，而不重复实现上游分析流程。

### 至少完成

- 提供两个不同有效 ticker 和一个共同 `YYYY-MM-DD` 日期作为输入。
- 顺序调用上游现有 graph 分别分析两个标的；不新增 provider，不要求并行执行或组合模拟。
- 保存每个标的的原有完整报告，并生成一份比较 Markdown，至少包含 ticker、日期、运行状态、最终评级/`REVIEW`、摘要和完整报告路径。
- 某一 ticker 失败时保留另一 ticker 的成功结果，并为失败项显示原因。

### 完成标准

- 两个固定离线 mock 结果可生成一份比较报告，字段/顺序符合批准的输出契约。
- 分别模拟第一项失败和第二项失败：成功的那项报告都仍存在；失败项不得被填成有效评级。
- 覆盖重复/非法 ticker、未来日期、部分失败、两项均失败；证明两 ticker 的报告、评级和数据没有交叉错配。
- **NFR-A：**两个运行中任意一个失败时，成功报告保留率为 100%；使用离线 mock graph 注入失败并由测试自动断言。
- PR 关联 FR-A 与 NFR-A，包含需求追踪、正常/负向测试、使用说明、AI-use log 更新、同伴评审和 CI 结果。

## 3. B：FR-B 跨标的共同事件归并

**目标**：让模型阅读具体新闻内容，并找出同时涉及至少两个标的的同一底层事件。这里的“热点”指跨标的共同新闻主题，不等于全市场热度或事件影响力排名。

### 最低输入与范围

- 输入 2–3 个 ticker，回看窗口不超过 7 天。
- 对每个 ticker 使用上游已有新闻数据能力，最多取 5 条记录；每条输入都分配本次运行唯一的 evidence ID，并保留 ticker、日期、来源和模型可读的标题/内容片段。
- 将本次所有限定记录作为一组交给模型进行事件归并，最多一次归并 LLM 调用；不得逐条新闻分别调用模型。
- 不增加新闻供应商、不做未来价格预测、不计算热度分数、不排列影响力、不要求社交网络趋势分析。

### 输出与失败行为

- 每个归并事件输出简短摘要、涉及的 ticker，以及支持该事件的 evidence ID、来源和日期。
- 一个事件须至少有两个 ticker 的输入记录作支持。
- 无法确认属于同一事件的记录留作未归并，不得强行配组。
- 无可用新闻应标记数据不可用/无记录；有新闻但未发现跨 ticker 共同事件时，才可报告没有发现共同事件。
- 确定性 validator 检查 evidence ID 是否属于本次输入、ticker/date 是否与该记录相符；validator 失败时，该条不得作为已验证事实输出。

### 完成标准

- 团队准备固定、人工标注的离线评估样例：至少涵盖同一事件、不同事件、同标的重复报道、时间窗口外报道、无数据和证据不足。
- 模型输出符合结构化 schema；同事件有来源支持，不同事件不应因共享泛化词语而强行归并。
- 离线测试 mock 模型输出，覆盖合法分组、伪造 evidence ID、错配 ticker/date、单一 ticker 事件和无记录状态。
- 固定语义评估集至少含 20 对人工标注的新闻记录，其中至少 10 对为同一事件、10 对为不同事件；pairwise precision 不低于 0.80、recall 不低于 0.70。每次 prompt/model 变化均记录模型/provider、样例版本和 precision/recall；CI 评估未达阈值则阻断变更。团队应在编码前共同审阅并冻结标注集。
- **NFR-B：**所有输出 evidence ID 的解析率为 100%，伪造/跨运行 ID 为 0；由确定性 validator 测试验证。
- PR 关联 FR-B 与 NFR-B，包含固定评估记录、来源策略、prompt 变更记录、测试和同伴评审。

## 4. C：FR-C 运行 Manifest 与本地查询

**目标**：每次运行的基本配置与产物路径能够被机器读取，并可从本地结果目录按标的/日期找到。

### 至少完成

- 每次成功或失败的运行在其结果目录写入 `run_manifest.json`。
- 字段至少包括：schema version、run ID、ticker、asset type、analysis date/as-of、开始/结束时间、代码版本（可取得时）、所选分析员、模型/provider 标识、配置的数据供应商、运行状态、报告相对路径及错误/未知字段说明。
- 供应商字段准确标记为“配置的数据供应商”，不得声称是每项数据请求的真实返回来源；无法取得的值用批准的 unknown/null 表示。
- 增加 CLI 查询命令，支持 ticker 和/或日期过滤，并显示匹配的运行及报告路径。
- 查询遇到单个坏 JSON、未知 schema version 或缺失报告时显示警告并继续，不修改/删除报告。
- manifest 不得保存 API key、secret 值、凭证 URL 或真实账户隐私。

### 完成标准

- 两个固定 manifest 能被写入、schema 校验并通过 CLI 查询得到正确结果。
- 测试覆盖无筛选、ticker 筛选、日期筛选、无匹配、坏 JSON、未知 schema、报告缺失、secret 字段及不安全路径。
- 单个损坏 manifest 不影响其余有效 manifest 的结果。
- **NFR-C：**在固定 CI runner 上对 1,000 个合成 manifest 查询不超过 2 秒；使用版本化生成器和脚本测量。若基线测量显示此值不适用，应在实现前由团队确定替代阈值。
- PR 关联 FR-C/NFR-C，更新 schema、使用说明、AI-use log 和追踪矩阵，并通过 CI/同伴评审。

## 5. D：FR-D 确定性决策资格门与项目协调

**目标**：确保关键市场证据未通过确定性资格检查时，LLM 无法给出可行动评级。

### 至少完成

- 团队决策模式要求 market analyst 被选中；其市场数据执行结果应提供明确的机器可读状态，至少区分有效、不可用和未执行。
- 最终评级提交给调用者/报告前，由确定性代码检查 market evidence status 和日期：未执行、缺失、不可用或晚于分析日期时强制将权威 `final_rating` 置为 `REVIEW`，并记录触发原因。
- 最终评级不属于上游允许的 `Buy`、`Overweight`、`Hold`、`Underweight`、`Sell` 集合时，同样置为 `REVIEW`。
- 若 gate 失败，即使模型正文写有 `Buy`，CLI、报告和机器可读结果也必须以 `REVIEW` 为准。
- 只把上述关键条件列为阻断项；其它分析员缺失按团队 runtime policy 处理，不自动扩大安全门范围。
- D 同时维护会议/里程碑、依赖阻塞、集成状态和 PPT 合并进度；安全规则、阈值及 PR 结论由团队共同审阅，D 不批准自己的安全改动。

### 完成标准

- 正常市场证据和有效评级通过；逐项注入未执行、缺失、不可用、晚于 as-of、未知评级时均得到 `REVIEW` 及正确原因。
- 至少有一个冲突负向测试：模型输出 `Buy`、市场状态不可用，最终 `final_rating`、CLI 和保存报告均显示 `REVIEW`。
- gate 为确定性函数或可隔离组件；离线测试不调用真实模型/API。
- 不变量登记、ADR、追踪矩阵、结构/安全 CI 检查和非 D 人工评审齐全。
- **NFR-D：**所有预先列出的 gate 绕过负向用例中 bypass 数为 0；测试集固定并由 CI 自动执行。
- D 的协调工作留有真实任务/决策/阻塞记录，不代替其他人的模块实现、测试或个人贡献证据。

## 6. 四人共同完成定义

1. 四项 FR、四项 NFR 均在 `requirements.yaml` 中有唯一 ID、Owner、MoSCoW、机器可检查 fit criterion、阈值和验证方式；NFR 阈值在实现前批准。
2. 每项功能有正常和负向离线测试；安全不变量有违反即失败的测试。每项测试引用需求或不变量 ID。
3. OpenCode 编码先经人工批准计划；PR 说明上游基线/团队增量、范围、接口、失败路径、测试结果和影响的需求。
4. PR 更新 `docs/ai-use-log.yaml`；适用时同步 ADR、invariants、trace matrix、review memo、debt/bug diary。
5. CI 运行项目规定的 lint、类型、依赖、schema、安全/权限、固定模型评估和全回归检查；门禁实际生效后才能声称已完成。
6. A–D 每人提供自己的 PPT 内容：需求、设计、实现、测试/测量结果、人类监督证据和实际贡献；D 汇总，所有成员校对。
