# CS5351 小组项目要求 v4

> 团队确认草案。课程交付要求依据课程项目规格、课程介绍和教师补充说明整理。课程通知或教师最新说明优先。成员用 A、B、C、D 代称，正式提交时使用真实姓名和学号。

## 1. 项目目标

在现有 TradingAgents 代码基线上，使用 OpenCode 和可审计的人类监督完成有明确需求、架构约束、验证证据和工程治理的增强。项目须保留 TradingAgents 的 AI 应用能力，并至少包含一项由确定性代码执行的安全相关边界。模型输出不能覆盖该边界。

四名成员各负责 **一项功能需求（FR）和一项非功能需求（NFR）**，全组共形成四项 FR 和四项 NFR。项目定位为金融分析研究工具，输出用于研究分析。团队贡献以新增或实质修改的组件及实际工程工作为准。

## 4. 四项 FR 的统一行为约束

### FR-A 同日双标的对照报告

用户提供两个不同的有效标的和一个共同分析日期。系统分别调用上游现有分析流程，生成一份汇总 Markdown 报告，至少列出每个标的的运行状态、最终评级或 `REVIEW`、简要结果和完整报告路径。

两次运行可顺序执行，交付范围限于同日分析对照。任一标的运行失败时，保留另一个标的的成功结果，并在失败项显示原因。数据、评级和报告须对应正确的标的。

### FR-B 跨标的共同事件归并

用户提供 2–3 个标的和最多 7 天的回看窗口。系统从现有新闻数据中取得每个标的最多 5 条记录，将标的、日期、来源 ID 和标题或内容片段交给模型。模型根据新闻内容判断记录是否描述同一具体事件，并生成简短摘要。热度评分、影响力排序和价格预测均在本模块范围之外。

每个输出事件至少关联两个标的，并列出被归并的新闻来源 ID、标的和日期。证据不足的记录保留为未归并项。没有可用记录时标记“数据不可用”或“无记录”。只有在有可用记录且未检测出跨标的共同事件时，才报告“没有发现共同事件”。

确定性校验须确认引用的来源 ID 来自本次输入，且标的与日期匹配对应记录。只展示通过校验的事件证据。用固定人工标注样例评估模型对同一事件的判断，证据引用校验按 NFR-B 单独验证。

### FR-C 运行 Manifest 与本地查询

每次分析运行在结果目录保存 `run_manifest.json`，至少包含 schema version、run ID、代码版本或 commit（可取得时）、标的、资产类型、分析日期或 as-of、起止时间、所选分析员、模型和供应商标识、配置的数据供应商、运行状态及报告相对路径。数据供应商字段标明是配置值。未知值用 `null` 或 schema 定义的 unknown 状态表示。

CLI 按标的、日期或两者查询运行清单，并显示对应报告路径。查询只读结果目录，无需外部服务。单个清单损坏、缺失或版本不受支持时，提示原因并继续查询其他记录。清单使用允许的字段记录运行信息，排除密钥、含凭证的 URL 和敏感账户数据。

### FR-D 确定性决策资格门

在团队决策模式中要求 market analyst 参与。最终输出前，由确定性代码检查关键市场证据和评级。market analyst 未运行、市场快照缺失或不可用、快照日期晚于分析日期，或评级不在五级允许值内时，最终结果为 `REVIEW`，并提供机器可读及用户可见的触发原因。

证据有效性来自实际数据和执行状态。资格门给出的评级是 CLI、报告与机器可读结果使用的权威评级。其他非关键分析源缺失时按运行时策略降级。

## 5. A–D 的 NFR 指标与验收

| 成员/ID | NFR | 指标及验收阈值 | 验证方法 |
|---|---|---|---|
| A / NFR-A | 部分失败恢复 | 双标的运行中，任一标的失败时，另一标的成功报告的保留率为 100%。 | 固定 mock graph，分别注入第一个和第二个标的失败。 |
| B / NFR-B | 证据可追溯性 | 输出证据 ID 的解析率为 100%，伪造或跨运行 ID 数为 0。 | 用确定性校验器核对固定样例，加入非法 ID 和跨运行 ID 的负向测试。 |
| C / NFR-C | 响应性能 | 在固定 CI runner 上查询 1,000 份合成 manifest，墙钟时间不超过 2 秒。 | 固定生成器、机器类型与计时脚本，重复运行并记录结果。若基线证明目标不可行，在实现前批准替代阈值。 |
| D / NFR-D | 安全资格 | 预先列出的关键证据失败用例中，资格门绕过次数为 0。 | 构造模型评级 `Buy`，注入缺失、不可用或晚于 as-of 的关键证据，并验证最终 `REVIEW`。 |

按 D1 登记四项 NFR 的输入、环境、阈值、验证命令和通过条件。实现前用固定样例或 CI 环境核验并批准目标值。

## 8. 原仓库并入及结构迁移方案

1. 核对上游 URL、锁定 commit、许可证和干净工作树。以该 commit 建立团队仓库并保留上游历史。上游官方仓库用 `upstream`，团队 GitHub 仓库用 `origin`。
2. 在同一仓库加入团队交付文件。同名文件包括 `README.md` 和 `pyproject.toml`，以可审查的增量修改接入。
3. 按上游原布局先运行基线测试并留证，再以独立迁移提交将应用包和 CLI 移至 `src/tradingagents/`、`src/cli/`，把上游 `tests/` 按实际依赖归入 D8 指定的目录。同步调整包发现、CLI、资源路径、pytest 和 CI。
4. 迁移后验证包安装、CLI 启动、资源发现、离线回归、live 测试收集以及缓存和报告路径，再集成 A–D 功能。提交树中保留一套源码和一份 Git 历史，以 `docs/baseline.md` 标出迁移与增强的提交边界。

## 9. 必交成果 D1–D9

### D1 — 机器可读需求

- `docs/req/requirements.yaml` 使用 YAML 表达产品需求，兼作统一需求注册表和机器可读 PRD。Introduction 第 24 页将该文件标为 machine-readable PRD。
- 每条记录至少含 ID、类型、需求陈述、可机器检查的 fit criterion 和 MoSCoW 优先级，并说明来源与取舍。团队需求同时标明负责人及验收人。
- 类型覆盖功能、不变量、质量属性、性能、成本、治理和安全。不变量是不可妥协的规则，验收实行零容忍。NFR 使用指标、阈值和验证方式。
- 纳入基线分析发现的相关需求并关联来源，区分既有能力、需保持的约束、本次影响范围和新增或修改需求。
- `docs/req/req-schema.json` 定义注册表的 JSON Schema。CI 校验见第 12 节。

### D2 — 架构文档

八类必需工件均使用 Markdown，权威正文放在 `docs/architecture/`。根目录 `architecture-blueprint.md` 仅保留指向 `docs/architecture/architecture-blueprint.md` 的 Markdown 链接。

| 工件 | 应包含的内容 |
|---|---|
| `architecture-blueprint.md` | 范围、驱动因素、系统与组件边界、建议性和权威性决策的分界，以及 agent 工作流、权限、验证、可观测性和变更政策。 |
| `adr/001-<decision>.md` 等 | 设计问题、比较过的方案、选择理由、后果及重新考虑条件。记录 AI 上下文分层和组装流程、Token 预算、压缩阈值、关键约束重新注入政策。 |
| `invariants.md` | 各不变量的陈述、来源需求、负责执行的组件、验证方法及违反后采取的具体兜底动作。 |

### D4 — 验证治理与质量记录

`docs/code-governance/verification-constraints.md` 规定每个验收标准至少对应一个测试，每个不变量至少有一个在被违反时会失败的测试。测试须引用需求或不变量。每轮验证运行全部此前测试，要求零回归。

1. **结构验证**检查导入、架构和组件边界、权限，以及实现是否符合架构约束。
2. **回归验证**检查此前测试套件是否全部通过。
3. **行为验证**依据可测质量阈值检查应用行为，例如忠实度、相关性和零安全逃逸。

| 持续维护的文件 | 应包含的内容 |
|---|---|
| `docs/review-memo.md` | 每个 PR 的需求、架构、代码、测试、运行元数据、安全和效率评审，结论为 `APPROVE`、`CHANGES REQUIRED` 或 `REJECT`。 |
| `docs/debt-register.md` | 记录提示词腐化、虚构或隐藏依赖、难改代码、agent 膨胀、评估债、护栏债和人类认知债等技术债。 |
| `docs/bug-diary.md` | 记录显著缺陷的症状、复现、分类、根因、修复及暴露的不变量缺口。 |

### D5 — 带人工注释的 Agent 会话记录

- 在 `transcripts/` 保留完整原始会话，文件名体现学号和姓名。以注释标记真实的人工中断、重定向、批准和拒绝，并解释理由。注释与原始记录须同时保留。
- 会话合起来覆盖六个过程环节：需求分类、架构候选与评估、编码前计划批准、团队组件构建、验证合规、根据测试证据修订架构。
- 按规格总体提交说明准备 **5 份**。D5 正文和目录示例与总体说明在数量或组织方式上的表述有差异，最终提交格式以课程确认为准。团队需为四名成员和六个过程环节安排实际覆盖。
- 按教师对基线的澄清，构建证据针对团队由 agent 实现的新增或实质修改组件。以锁定的上游基线标明贡献边界。

### D6 — 过程报告

- 根目录 `Report.md` 是单一 Markdown 文件，列出四名成员的姓名、学号和相对贡献。相对贡献的平均值为 **1.0**，分配依据实际工作与证据。
- 正文不超过 **10,000 words**，图示不计入。按 **12 号字、单倍行距排版时超过 15 页**。Markdown 渲染和页数计算方式以课程确认为准。
- 说明软件工程流程及其改进。用需求变化、缺陷趋势或歧义解决等实例展示过程质量，说明工件如何随变更同步演进，以及人类监督发现了哪些 agent 未发现的问题。
- 每位成员提供简短个人反思，课程示例长度为 **300–500 words**，注明姓名和学号。

- `docs/ai-use-log.yaml` 按相关 PR 记录 coding agent、需求、实际会话引用、人工监督、变更与验证结果，提交时保持最新。

### D8 — 源码与测试

- `src/` 放置完整应用源码，模块名称与架构元素对应。上游源码的具体适配方式见第 8 节。
- `test/` 放置完整测试。`test/offline/` 包含无需网络或密钥的确定性测试，默认 CI 运行。`test/live/` 包含需要 API 的测试，独立标记并说明运行方式。`test/fixtures/` 放置适用的固定样例、模拟响应和预期结果。

### D9 — 静态启动提示词

Coding agent 从 `AGENTS.md` 进入项目后读取根目录 `Prompt.md`，先提出包含需求追踪、接口契约、范围、测试策略和执行步骤的计划。**生成代码前必须停止，等待人工批准。** 后续构建和自验证也按阶段经过人工关卡。

根目录 `Prompt.md` 是开发用启动指令。`prompts/` 用于需要版本管理的应用运行时提示词及其评估信息。

## 12. CI/CD 强制阻断门禁

| 门禁 | 触发时机与通过条件 | 失败后的阻断 |
|---|---|---|
| 测试审批 | 关联测试须在实现开始前获批，代码变更须有可核对的审批记录。 | 缺少事前批准的代码变更不得合并。 |
| 静态分析 | 每次 commit 运行 lint、类型和依赖检查。触及安全相关路径的 PR 额外检查契约、安全、API surface 和权限。 | 任一适用检查失败即阻止合并。 |
| Schema | 验证 `docs/req/requirements.yaml` 符合 `docs/req/req-schema.json`。 | 注册表校验失败即阻止合并。 |
| 语义评估 | prompt 或模型变化时，使用固定评估集复核已批准的质量阈值，并记录结果。 | 未达标则报告失败，阻止合并和进入生产。 |
| 回归 | 每次变更运行全部既有回归测试。 | 任一回归阻止合并。 |
| AI 使用日志 | 修改代码或 prompt 的 PR 须更新 `docs/ai-use-log.yaml`。 | 日志未更新即阻止合并。 |

分支保护须将 CI 通过设为合并条件。安全关键变更还须经过人工评审，并附对应的架构决策。验收以实际运行的 workflow、分支保护设置和能说明阻断行为的证据为准。
